# AI 產出可信度守則（常駐核對文件）

> 產出者：AI 助理（依 BOSS 2026-10-05 指示整理）
> 緣起：BOSS 分享 YouTube《tnVAO6Dm9F4》——「AI 可以幫你整理財報、研究股票，但它給的數字可能根本不是公司公布的，而你從答案本身看不出來。」
> 用途：**每一輪建置（新端點、資料接線、歸因分析、報告產出）都拿來逐條核對。** 這不是哲學宣言，是可操作的檢查清單。
> 適用範圍：GOD 平台／股市峰子全部資料產出與分析層。

---

## 0. 核心信念（一句話）

**「看似工整、完整、合理」是 AI 產出最危險的狀態——因為它讓所有人都停止懷疑。**
本守則的唯一目的：把「懷疑」制度化，讓它在流程中強迫發生，而不是依賴某人的警覺心。

YT 原片的三個防錯動作，對應到我們的工程實務：

| YT 建議 | 我們的工程化版本 |
|---|---|
| ① 在問題後面加上規則 | → 每個 agent 的 `identity.md` 明文寫「缺值怎麼標、不準補腦」 |
| ② 把你真正想知道的列成具體問題 | → 驗收時不比狀態碼，比**逐欄位 diff** 與**內容豐富度** |
| ③ 你最在意的數字自己回原文對一次 | → **每個端點遷移都做「線上即時 vs 本地預算」diff**；關鍵數字回溯上游原始檔 |

## 1. 五大陷阱（本專案已實測踩過或差點踩過）

每條都附**真實案例**，不是假設。

### 陷阱 A — 「誠實降級」掩蓋缺陷
**症狀**：端點回 200、格式合法、甚至標註了缺口，但資料少了一半，使用者無從察覺。
**實例**：`block-trades` 有 **83% 請求抓不到上櫃（TPEX）**，只回上市部分。狀態碼 200、schema 通過、`gaps` 有寫——**只看表面全是对的**。根因是邊緣端對特定政府伺服器間歇性不可達。
**鐵律**：
- 任何有 `gaps` / `fallback` / `optional` 設計的端點，**遷移時必做逐欄位 diff**。
- 「有標註缺口」不等於「缺口被注意到」。**要主動量化缺口比例並回報**，不能只塞進 metadata。

### 陷阱 B — 死掉的上游會回 HTTP 200
**症狀**：引用的 API 根本不存在，但網址 302 導向 404 網頁、回 **HTTP 200 + HTML**。程式吞掉解析錯誤、靜默回空陣列。
**實例**：`uptrend` 引用的 `MI_DAILYKLINE` **從未存在過**（查 swagger.json 確認 143 個端點無一 KLINE）。整支端點自始至終沒吐出一根 K 棒，卻看起來「正常」。最後連帶發現它是建立在一份**已被更正掉的規格誤判**上。
**鐵律**：
- **上游「存在性」必須實測驗證**，不可假設文件寫的 URL 能用。
- 驗證法：跟隨重導向（`curl -sL -w '%{url_effective}'`）＋ 比對 `swagger.json` 端點清單 ＋ **檢查回應內容**（HTML ≠ JSON）。
- **「狀態碼 200」≠「功能正常」**。契約驗證必須涵蓋**內容豐富度**。

### 陷阱 C — 「契約驗證通過」不等於「有資料」（偽陽性就緒）
**症狀**：schema 的 `required` 欄位很少且 `additionalProperties: true`，所以**空殼也能通過驗證**、被標成 PASS 上架。
**實例**：`sector-sniper` 回 `items: []`、`score: null`、成分全 `DATA_INVALID`，**但 `internal_status: "PASS"`**。更狠的是「有說明文字的空殼」——用大量描述文字灌滿 `richness`，讓「有效值數量」計量失真。
**鐵律**：
- 判定「有沒有資料」要用 `richness(payload) > 0`，且**先列黑名單**（哪些欄位永遠不是資料，例如純說明文字）。
- **前端必須自己做一次資料可用性判定**，不能完全依賴後端的 `internal_status`。後端標註是「產出端的誠實」，前端還要有「消費端的懷疑」——兩層都要有，因為快取會讓後端修正延遲生效。

### 陷阱 D — 把常識包裝成數據
**症狀**：AI 把「大家都知道的原因」寫得像精算結論。例如「台積電漲是因為 AI 需求旺盛」——這句話永遠對、永遠無法證偽、也永遠沒有資訊量。
**實例**：歸因引擎探索階段實測——**最能自圓其說的解釋，預測力反而最差**。「今天大盤大漲且個股相對強」這個聽起來最有說服力的條件，隔日勝率只有 **41.9%（比不看還差 8.8pp）**。台積電 R² 高達 80.7%，意思是它八成波動都被大盤解釋完了，個人幾乎沒有可利用的殘差。
**鐵律**：
- **「能解釋」≠「能預測」**，前者越強越容易誤導後者。驗收唯一方法：**拿去測未來並與基準比較**。
- **勝率必須配 n 與 95% CI**。`72.7% (n=11)` 是雜訊。**不報基準的勝率沒有意義**。
- **歸因第一步永遠是「先扣掉大盤」**，否則把大盤的功勞錯記到個股消息面。
- 不同股票歸因結構差異極大（R² 4.7%~80.7%），**同一份原因清單不可套用所有股票**。

### 陷阱 E — 照著舊規格／幻覺施工
**症狀**：某個功能是「照某份 spec 做的」，但那份 spec 已被更正、或根本是誤判。
**實例**：見陷阱 D 的 `uptrend`——route 註解引用**已被刪除的舊版 §2**，一整支端點建立在幻覺上。連預設代號的註解都對不上實際解析結果（雙重錯誤）。
**鐵律**：
- **凡是「照某份 spec 做的」，動手前必須確認那是不是最新版**（本專案 `Front-end/screens/*.md` 有「舊版／重做版」之分，重做版的 §0 就是更正紀錄）。
- **預設值／常數也要交叉驗證**：註解寫的名稱和實際解析對不上，是「這段程式沒人驗證過」的強烈訊號。

## 2. 資料誠實三铁律（不可違反）

這三條是底線，違反任一條 = 該產出不准上架。

1. **無資料就明說**：缺值一律回 `null` + `unavailable_reason`，**絕不用假資料補腦、絕不拿舊資料冒充新的**。
   - 例：TDCC 週變化需累積一週，首次接線只有一期 → 明確標 `status: WARMING_UP`，`delta_1w` 老實回 `null`。
2. **缺值寫法要一致**（本專案已定案的三套慣例）：
   - 原始數值（`number`/`integer`）→ `null`
   - 格式化字串（UI 顯示用）→ `"—"`
   - Hive 內部狀態 → 標記字串（如 `DATA_INVALID`）；App 狀態欄位 → `ok`/`checking`/`unavailable`
   - ⚠️ **Hive 推理階段的「標記字串」慣例，寫進 App 契約 payload 時必須轉換**，不可直通。
3. **空殼不得覆蓋有內容的既有檔**（連 `--force` 也不行）。排序用「檔名日期 → 內容豐富度 → mtime」，**不可只用 mtime**（補寫檔會讓舊日期 mtime 最新 → 蓋掉真資料）。

## 3. 每輪建置的強制檢查清單

開始動工前，逐條打勾。**任何一條答不出來，就先回去查，不要猜。**

### 3.1 接線新資料源／新端點時
- [ ] 這個上游 URL **實測過嗎**？跟隨重導向後的最終內容是 JSON 還是 HTML？
- [ ] 它在官方 `swagger.json`／文件裡**真的存在**嗎？（不是憑印象或抄別的專案）
- [ ] 它的資料**多久更新一次**？在我們預算了時間點（16:35？）已經**定稿了嗎**？若否，需要第二場次嗎？
- [ ] 它有幾個分級／欄位／編碼陷阱？（參照 TDCC 的 17 級坑、尾隨空白、代號非 4 碼）
- [ ] 缺資料時，我的代碼會回 `null`+reason，還是會悄悄補 0／補舊值？

### 3.2 遷移／改寫既有端點時
- [ ] **這個端點現在是好的還是壞的？**（決定嚴格模式 vs 寬鬆模式，見下）
- [ ] 找過所有**消費者**（`grep -rn '<路徑>' src/`）並讀過它怎麼驗證回應嗎？
- [ ] 做過**遷移前 CPU 分佈 baseline** 嗎？（HTTP 200 ≠ 沒有 CPU 問題）
- [ ] 做過**「線上即時 vs 本地預算」逐欄位 diff** 嗎？（同時驗證正確性＋揪靜默缺陷）
- [ ] 把純函式從 route 抽走時，**同步更新了所有 import 它的 test/client** 嗎？

### 3.3 產出分析／歸因結論時
- [ ] 這個結論**能不能證偽**？還是「永遠對、沒資訊量」的常識？
- [ ] 有沒有**先扣掉大盤**再談個股原因？
- [ ] 報出的勝率有沒有配 **n 和 95% CI**？有沒有**對比基準**？
- [ ] 這是「能解釋」還是「能預測」？如果是後者，**拿歷史外推測過了嗎**？

### 3.4 宣稱「完成／結案」時（結案紀律）
- [ ] `git status` 乾淨？
- [ ] **線上驗證過**（不是只有本地測試）？
- [ ] 任務清單無 in_progress 殭屍？
- [ ] 記憶已更新？
- [ ] 回報了三個數字：結案數／新增數／淨變化？

## 4. 兩種模式的判斷（選錯會把好頁面改壞）

判斷依據**只有一條**：**這支端點「現在」是好的還是壞的？**

| | 嚴格模式 | 寬鬆模式 |
|---|---|---|
| 未命中行為 | `200 + ready:false` | 降級回即時計算 |
| 適用 | 現況**已經壞了**（1102／502／`ok:false` 無資料）→ 回 `ready:false` 是改善或等價 | 現況**仍回 200 且有真實資料** → 回 `ready:false` 會把可用頁面改壞 |
| 已採用 | market-overview／trading-dates／treemap／trump-radar／margin-maint | dividend-calendar／block-trades／etf-active |

⚠️ **反直覺的關鍵**：「前端會壞」**不等於**「要用寬鬆模式」。要問「**前端現在是不是已經壞了**」。
（`trump-radar` 的前端同樣要求 `ok===true`，回 `ready:false` 一樣進錯誤狀態，但它遷移前就回 `{"ok":false}`——前端本來就是壞的 ⇒ 嚴格模式與寬鬆模式對使用者等價，而寬鬆模式只會多燒 8.48 秒逾時再失敗。）

## 5. 量測方法的自我防騙（別讓工具騙了自己）

這些是「验证过程本身可能出错」的教训，同样属于「看似正确实则错误」家族：

- **連打式量測會污染 CPU 結果**：短時間送 20–30 請求會讓 Cloudflare 頻繁建立 isolate，模組實例化成本被算進 cpuTime → 出現 100–270ms 假尖峰。**改用節奏量測（間隔 0.8s）**。若不做三步追查（懷疑冷啟動→四端點交錯→改節奏），會把量測假象誤判成端點缺陷。
- **部署後有全球傳播延遲**：完成後 6 秒內的請求會拿到舊版 code。**驗證前至少等 20–30 秒**。
- **`wrangler tail` 事件會掉**：送 30 筆可能只收到 11 筆。量測後等 25–30 秒再 kill，以樣本數判斷可信度。
- **報告要給分佈，不要只給單一數字**：min/p25/median/p75/max ＋ 達標比例。
- **看到「全部 0 命中」先懷疑語法**（沙箱 BSD grep 的 `\|` 交替會靜默失效），不是急著下「沒有」的結論。
- **能載入 ≠ 合法**：plist 用 `plutil -lint` OK，嚴格解析器可能拒收。改完要同時用嚴格器驗。

## 6. 使用方式（给未来的自己和 BOSS）

- 每輪開工前，把 §3 的對應清單貼到工作筆記逐條過。
- 發現新陷阱 → 追加到 §1，並標註實測日期與證據檔案路徑。
- **本文件本身就是「把懷疑制度化」的产物**：如果某一輪跳過了核對，那就是本文件的失效，不是「這次特殊」。

> 最後一句提醒（呼應 YT 原片精神）：
> **我們最怕的不是「產出是錯的」，而是「產出看起來太對了，以至於沒有人再去查。」**
> 每一次想說「這個應該沒問題」的瞬間，就是本文件存在的理由。
